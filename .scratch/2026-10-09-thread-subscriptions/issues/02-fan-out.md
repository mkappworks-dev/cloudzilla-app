# Fan-out respects thread subscriptions

Created: 2026-10-09
Category: enhancement
Status: done
Blocked by: 01

## What

Rework recipient selection in `internal/service/notification_service.go` so `NotifyIssueComment`, `NotifyPRComment`, `NotifyIssueStateChange`, `NotifyPRStateChange`, `NotifyPRReview` and `NotifyDiscussionReply` share one path. It sends to subscribers, watchers and the author, and drops the actor and muted users. `NotifyDiscussionReply` gets watcher fan-out only if it already has it today (it currently notifies just the author); otherwise it gains subscriber fan-out only.

- `NotifyMention` ignores a mute and calls `SubscribeOnMention`.
- Immediate email goes to the author and to `subscribed` rows; watchers without a row get none.
- Migration 115 adds nullable `notifications.subject_kind`, backfilled from `type` (and `subject_url` for mentions). Every `Notify*` call sets it. `repo_transfer` stays null.

## Acceptance criteria

- [x] A muted user who also watches the repo gets nothing from a comment, review or state change.
- [x] A subscribed user in a repo they don't watch (or `ignoring`) gets the in-app notification and the immediate email.
- [x] A muted author is not notified; an unmuted author on a pre-feature thread still is.
- [x] A mention reaches a muted user and flips the row to `subscribed`.
- [x] `CanRead` and actor-silence rules still hold.
- [x] Backfill migration test covers each type and a mention URL of each kind.
- [x] `docs/notifications.md` updated: fan-out rules, email, `subject_kind`.

## Agent Brief

**Category:** enhancement
**Summary:** Make notification recipients depend on thread subscriptions: subscribers get notified, muted users don't, mentions break through.

**Current behavior:**
Issue/PR comments, reviews and state changes notify the subject's author plus every non-ignoring repo watcher. Discussion replies notify only the author. Mentions always notify the mentioned user. Immediate email goes only to the direct recipient. A notification does not record which kind of thread it belongs to; only the number and URL.

**Desired behavior:**
For a comment, review or state change, recipients are the thread's subscribed users, the repo's non-ignoring watchers and the author, minus the actor, minus muted users, minus anyone who can't read the repo. An author with no row on a pre-feature thread is still notified. A mention notifies the user even if muted and flips their row to subscribed. Immediate email goes to the author and to users with a subscribed row; watchers without a row stay in-app and digest only. Each notification stores its thread kind; existing rows are backfilled from their type, and mentions from the URL's section. Repo-transfer notifications have no kind.

**Key interfaces:**
- The `Notify*` methods of the notification service share one recipient-selection path.
- The notification model gains a nullable thread kind, persisted and returned by the store.
- The mention path calls the thread-subscription service's subscribe-on-mention.

**Acceptance criteria:**
- [x] A muted user who watches the repo receives nothing from a comment, review or state change.
- [x] A subscribed user in a repo they don't watch (or ignore) gets the in-app notification and the immediate email.
- [x] A muted author isn't notified; an unmuted author on a thread with no row still is.
- [x] A mention reaches a muted user and sets their row to subscribed.
- [x] Read-access checks and actor silence still apply.
- [x] The backfill is tested for every notification type and each mention URL kind.
- [x] `docs/notifications.md` describes the new rules, email behaviour and thread kind.

**Out of scope:**
- Adding watcher fan-out to discussion replies beyond what subscribers imply.
- New notification types (e.g. for assignment).
- UI.
