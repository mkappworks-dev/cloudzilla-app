## What

Call `AutoSubscribe` from: `IssueService.Create`, `PullService.Create` and `DiscussionService.Create` (reason `author`); `CommentService.CreateForIssue`, `CreateForPull` and `DiscussionService.CreateReply` (`comment`); the PR review submit path (`review`); `AssigneeService.AddToIssue` and `AddToPull` (`assign`, subscribing the assignee, not the actor). - [x] A failing subscription write doesn't fail the request (test with a stubbed error).

## Agent Brief

**Category:** enhancement
**Summary:** Subscribe users to a thread automatically when they author, comment on, review or are assigned to it.

**Current behavior:**
Participation creates no subscription state; interest is inferred at notification time from authorship and repo watches.

**Desired behavior:**
Creating an issue, pull request or discussion subscribes the author (reason `author`). Commenting or replying subscribes the commenter (`comment`). Submitting a PR review subscribes the reviewer (`review`). Assigning someone subscribes the assignee, not the actor (`assign`). All use insert-if-absent, so the first reason is kept and a muted thread stays muted. Mentions are covered by the fan-out ticket. A failed subscription write is logged and never fails the user's request.

**Key interfaces:**
- The thread-subscription service's auto-subscribe operation, called from the issue, PR, discussion, comment, review and assignee services.

**Acceptance criteria:**
- [x] Each action creates a subscribed row with the right reason for the right user.
- [x] A later action by the same user on the same thread keeps the original reason.
- [x] Acting on a muted thread leaves it muted.
- [x] A forced subscription error doesn't change the request's result (tested).

**Out of scope:**
- Mentions.
- Sending a notification on assignment.
- Backfilling rows for existing threads.
