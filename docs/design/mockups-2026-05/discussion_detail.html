RFC: Should we add OpenTelemetry tracing to the git transport layer? #42

MK malith started this discussion yesterday · 8 replies · Q&A observability rfc
Answered — daisy's reply was marked as the answer.
MK malith started the discussion yesterday

Our git transport layer — both the HTTP smart protocol and the SSH server — is entirely pure Go, which gives us a clean place to add instrumentation without shelling out to a git binary.

I'd like opinions on wrapping OpenTelemetry spans around pack negotiation, ref advertisement, and the SSH auth handshake. Questions before anyone writes code:

  • Do we export to an OTLP collector, or keep traces in-process behind a debug flag?
  • Is the per-request span overhead acceptable on the hot push/fetch path?
  • Should this wait until after v1.0?

Not committing to anything yet — looking for a steer.

8 replies

DK daisy Answer replied 22h ago

Strong +1 on keeping traces in-process behind a debug flag to start. An OTLP exporter is a config surface we'd have to support forever; a flag we can iterate on freely.

Marked as answer by malith
YM yumi Answer replied 19h ago

The overhead worry is real for fetch. Could we sample — trace 1 in N pack negotiations rather than every one? That keeps the hot path cheap and still surfaces the slow outliers.

Marked as answer by malith
MK malith Answer replied 5h ago

Good steer, both. Plan: in-process spans behind a debug flag, with sampling on the fetch path. I'll write it up as a post-v1.0 item and link a tracking issue here.

Marked as answer by malith
