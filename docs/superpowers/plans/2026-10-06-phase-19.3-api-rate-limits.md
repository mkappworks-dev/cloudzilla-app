# API Rate Limits Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every request that isn't a static asset counts against a per-subject, per-resource budget, and clients see their budget in `X-RateLimit-*` headers.

**Architecture:** A global `middleware.APIRateLimit` runs after `CORS` and before the form parse. It resolves the subject itself (session JWT, PAT, OAuth token, else the client IP), classifies the path into `core`, `git`, `archive` or `search`, and charges a fixed-window counter. A PAT or OAuth token it looks up is stored in the request context, so `servePAT`, `serveOAuth` and `resolveGitUser` reuse it. The existing `middleware.RateLimit` keeps its signature and shares the counter.

**Tech Stack:** Go, chi, viper.

**Spec:** [`.scratch/phase-19.3-api-rate-limiting/spec.md`](../../../.scratch/phase-19.3-api-rate-limiting/spec.md), ticket [`01-rate-limits.md`](../../../.scratch/phase-19.3-api-rate-limiting/issues/01-rate-limits.md)

## Global Constraints

- `middleware.RateLimit(limit, window)` keeps its signature and behaviour.
- The limiter never grants access; a key only picks a bucket.
- A credential is looked up at most once per request.
- Comments state only a *why*, in one line by default.
- Stage files by explicit path. Never stage `.claude/`.
